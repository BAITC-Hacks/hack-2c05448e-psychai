# HackAlem — PsychAI

Общие правила безопасной работы AI-агентов (Hermes и Codex) в репозитории хакатона HackAlem AI.

## Проект

- Репозиторий: HackAlem AI hackathon.
- Рабочая папка: `C:\Users\razgl\Documents\Codex\hackalem`
- Git-репозиторий: `https://github.com/BAITC-Hacks/hack-2c05448e-psychai.git`

## 1. Рабочая область

- Работать только в текущем репозитории.
- Не изменять файлы или проекты за его пределами без явного разрешения пользователя.
- Не использовать другие локальные репозитории как рабочую область проекта.
- Не менять глобальные настройки инструментов, IDE, Git, Hermes, Codex или Windows без явного разрешения.

## 2. Git

Единственный допустимый remote:

`https://github.com/BAITC-Hacks/hack-2c05448e-psychai.git`

- Не добавлять, удалять или изменять remotes без явного разрешения.
- Не выполнять `git push` без явной команды пользователя.
- Перед запрошенным push проверить `git remote -v` и текущую ветку.
- Не делать force-push.
- Не переписывать историю Git без явного разрешения.
- Сохранять проверяемую историю разработки.
- Не выполнять операции Git, способные уничтожить незакоммиченные изменения, без подтверждения.
- Не изменять и не взаимодействовать с другими репозиториями вне этого проекта.

## 3. Безопасность

- Не удалять значительные объёмы файлов или данных без подтверждения.
- Не выполнять потенциально необратимые операции без подтверждения.
- Не использовать `git reset --hard`, force-операции, массовое удаление и аналогичные опасные действия без подтверждения.
- Не коммитить пароли, API keys, токены, credentials и другие секреты.
- Не публиковать секреты в GitHub, логах или документации.
- Не пытаться обходить ограничения безопасности, доступа или авторизации.

## 4. Поведение агента

- Не додумывать отсутствующие требования.
- Если существенная часть задачи неоднозначна и трактовки ведут к разным результатам — спросить пользователя.
- Если требуется важное продуктовое или архитектурное решение, отсутствующее в требованиях — предложить варианты и спросить.
- Не делать существенные изменения «на всякий случай».
- Не расширять scope задачи без необходимости.
- Перед потенциально разрушительными или труднообратимыми изменениями предупредить и получить подтверждение.
- Обычную работу в рамках задачи (правки файлов, стандартные команды разработки) выполнять самостоятельно, не запрашивая разрешение на каждый шаг.

## 5. Принципы разработки

- Приоритет — работающий и проверяемый MVP.
- Предпочитать простые решения преждевременной сложности и абстракциям.
- Работать небольшими вертикальными срезами.
- Не добавлять зависимости, сервисы и архитектурные компоненты без необходимости.
- Не оптимизировать преждевременно.
- После существенных изменений запускать соответствующие проверки и тесты.
- Не считать задачу завершённой только потому, что код написан: основная функциональность должна быть проверена.

## 6. Прозрачность

- Различать факты, требования, предположения и предложения.
- Не выдавать предположение за установленный факт.
- Если решение основано на неизвестном или непроверенном предположении — явно это обозначать.
- Не скрывать существенные ограничения, ошибки или неудачные результаты тестирования.
- Не заявлять, что что-либо проверено, если проверка фактически не выполнялась.

## 7. Сторонние материалы

При использовании стороннего кода, библиотек, моделей, датасетов, шаблонов или внешних сервисов:

- соблюдать соответствующие лицензии и условия использования;
- не выдавать стороннюю разработку за собственную;
- сохранять информацию, необходимую для раскрытия использованных материалов;
- не копировать существенные части чужого решения без соответствующего раскрытия.

## 8. HackAlem

Учитывать официальные правила HackAlem AI:

- основная разработка — в предоставленном командном GitHub-репозитории;
- сохранять проверяемую историю разработки;
- core functionality представляемого решения разрабатывается во время соревнования;
- AI-инструменты и AI-агенты разрешены;
- сторонние материалы используются законно и раскрываются;
- финальный проект должен иметь понятный README;
- README должен позволять другому человеку установить, запустить и проверить основной сценарий;
- финальная версия проверяема без доступа к личным аккаунтам участников;
- в ходе хакатона сохраняются промежуточные результаты разработки.

## 9. Независимость от домена

- Не предполагать заранее, что проект относится к психологии, медицине, логистике или иному домену.
- Домен, задача, требования и архитектура определяются только после получения официального задания HackAlem и решений команды.
- Не переносить правила или архитектурные решения из предыдущих проектов без явного основания.

## 10. Что НЕ является правилом

Не превращать `AGENTS.md` в подробную инструкцию конкретной реализации. Здесь только устойчивые правила поведения агента и разработки.

Не добавлять сюда:

- конкретную архитектуру будущего решения;
- конкретный стек до получения задания;
- психологические принципы;
- конкретные продуктовые требования;
- workflow конкретной задачи.
