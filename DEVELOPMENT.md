# Development Workflow — HackAlem

Лёгкий процесс разработки для 5-часового AI-хакатона. Подходит для одновременной работы
Hermes и Codex. Цель — работающий, проверяемый MVP и понятная история решений.

Постоянные правила проекта: `AGENTS.md` + `CONSTITUTION.md`.
Артефакты конкретной задачи: `spec.md` / `plan.md` / `tasks.md` (создаются под задание,
не являются правилами). Git-процесс регулируется `AGENTS.md` — здесь не дублируется.

## Поток (per task)

`Task → Understand/Clarify → Specification → Plan → Tasks → Implement → Verify → Demo/README`

### Task

Получить и зафиксировать задание HackAlem: brief, ограничения, критерии успеха, срок.

### Understand / Clarify

Прояснить неоднозначности задания. Допущения записывать отдельно и явно.
Если существенная часть задачи неоднозначна и трактовки ведут к разным результатам — спросить
пользователя (см. `AGENTS.md`, раздел «Поведение агента»).

### Specification (WHAT / WHY)

Зафиксировать, что строим, для кого, зачем и каковы критерии успеха.
Без преждевременного выбора реализации: никакого стека и архитектуры на этом шаге.

### Plan (HOW)

Определить архитектуру, стек, компоненты, модели данных, интеграции.
Сверить решения с `CONSTITUTION.md` (простота, наименьшее решение, обратимость).

### Tasks

Разбить Plan на конкретные небольшие задачи реализации, упорядоченные по зависимостям
(Setup → Core → Polish). Задачи — не правила, а артефакт текущей задачи.

### Implement

Выполнять задачи. Вносить изменения в рамках задания; при необходимости сверяться с Plan.

### Verify

Проверить реализацию против Specification и критериев успеха.
Записать, что проверено фактически, а что — нет. Не заявлять «готово», пока core scenario
не проверен (см. `CONSTITUTION.md`, разделы 2, 3, 7).

### Convergence (лёгкая финальная проверка)

Быстро сверить реализованное решение с заданием: нет ли незамеченных расхождений,
сломанной сборки, нераскрытых секретов. Это не многораундовый процесс — один осознанный проход.

### Demo / README

Оформить README: установка, запуск, проверка основного сценария, атрибуция сторонних материалов
(см. `CONSTITUTION.md`, разделы 8 и 10). README должен позволить другому человеку воспроизвести
основной сценарий без личных аккаунтов.

## Работа Hermes + Codex

- Источник истины — файлы репозитория, а не содержимое отдельного чата.
- Агенты избегают одновременного редактирования одного и того же файла; делят работу по файлам/областям.
- Существенные архитектурные или продуктовые разногласия передаются пользователю, а не решаются втихую.
- Не создавать параллельные конкурирующие реализации без явной необходимости.
- Сложный протокол синхронизации не требуется.

## Что НЕ является обязательным

- Отдельные checklist / analyze-фазы — только при реальной неоднозначности.
- GitHub Issues для каждой задачи — необязательно; `tasks.md` достаточно на 5 часов.
- Сложные процессы Spec Kit (CLI, `.specify/`, автоматическая синхронизация шаблонов).
- Обязательный `git pull` перед каждой работой и обязательные «частые маленькие коммиты» —
  Git-процесс целиком регулируется `AGENTS.md`.
- Дополнительные обязательные документы сверх `spec.md` / `plan.md` / `tasks.md`.

## История решений

Значимый выбор (стек, архитектура, сознательный отказ от функции) фиксировать кратко в Plan
или в сообщении коммита с обоснованием, чтобы сохранялись промежуточные результаты разработки.
